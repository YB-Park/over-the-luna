# v1.1 baseline evidence — probes 002 and 003

These are controlled, read-only Copilot runtime observations from the research branch. They are evidence, not a v1.1 routing specification.

Runtime for both probes:

- GitHub Actions on `YB-Park/over-the-luna`;
- Copilot CLI 1.0.80;
- checked-out plugin loaded with `--plugin-dir=.`;
- Main selected as `over-the-luna:over-the-luna`;
- model `gpt-5.6-luna`;
- tools limited to read-only repository inspection plus `task`/agent discovery;
- no repository mutation;
- OTel content capture disabled;
- raw Copilot event JSONL retained in the workflow artifact for routing/tool attribution.

Token values below are OTel usage values summed across model calls. They are useful for relative comparisons inside this experiment; they are not unique-context-size measurements.

## Probe 002 — broad automatic-core blast radius

Prompt archetype: trace every repository contract that enforces or documents the Luna-only automatic core and return the smallest coherent blast-radius set.

### Observed route

`Mode: SIMPLE — direct Luna`

- Agent invocations: 1
- Subagent invocations: 0
- Reviewer invocations: 0
- Model calls: 5
- Tool calls: 27 (`view`: 24, `glob`: 3)
- Mutation tools: 0
- OTel input tokens: 133,971
- OTel output tokens: 2,393
- Cache-read input tokens: 88,429
- Cache-creation input tokens: 45,527

The Copilot event graph attributes all 27 tool calls to Main. Main began with three repository-wide globs and then read 24 files, including all automatic/premium agent definitions, validator/runtime-test surfaces, public/design docs, release/contribution material, and the v1.1 research artifacts.

### Interpretation

The final answer was coherent, so this is not a correctness failure. It is a routing/context-isolation observation.

The task explicitly required tracing a repository-wide contract surface. Despite that breadth, the initial SIMPLE classification persisted through 24 reads. This strengthens the narrower `initial classification anchoring` hypothesis from Probe 001: some tasks can be correctly solved by Main while still consuming broad disposable discovery context that the current contract says should often be compressed through Architect.

This is evidence against the claim that the current policy consistently recognizes broad scouting after an early SIMPLE decision. It is **not** evidence that SIMPLE should be globally harder to select.

## Probe 003 — adversarial green-but-broken contract audit

Prompt archetype: find at most three high-risk cases where repository tests/validators could stay green while real VS Code semantics are broken because the checks merely mirror project assumptions.

### Observed route

`Mode: STANDARD — Luna Architect`

- Agent invocations: 2
- Subagent invocations: 1 (`Luna Architect`)
- Reviewer invocations: 0
- Model calls: 7
- Tool calls: 53 (`task`: 1, `view`: 42, `glob`: 10)
- Mutation tools: 0
- OTel input tokens: 275,530
- OTel output tokens: 5,078
- Main input/output tokens: 101,304 / 1,864
- Council input/output tokens: 174,226 / 3,214
- Cache-read input tokens: 213,456
- Cache-creation input tokens: 62,029

The event graph is important here: Main's only repository-level tool call was the `task` delegation. The Architect performed the 42 views and 10 globs and returned a compact ranked finding set. Main then synthesized the answer without re-reading the repository.

The audit identified concrete gaps including:

1. premium handoff UI/execution is only structurally checked in-repo and still requires real VS Code verification;
2. selected-tool inheritance is an assumed runtime contract that static/CLI validation cannot prove for VS Code;
3. mutation ownership is largely instruction-enforced while existing telemetry summarizes mutation tools globally rather than proving which agent executed them.

### Interpretation

This probe is evidence that the Council is **not globally dormant**. When the task framed consequential semantic uncertainty clearly enough, current v1.0 routing chose isolation and used it well.

It also corrects an earlier provisional reading of the trace: there was **no Main re-hydration of the Architect's 42-file exploration** in this run. Once isolation was selected, the ownership/context boundary was clean.

The interesting contrast is therefore not `Council works` versus `Council does not work`. It is that two repository-wide read-only tasks crossed the routing boundary differently:

- broad blast-radius tracing: SIMPLE, Main owns 27 discovery calls;
- adversarial semantic audit: STANDARD, Main delegates discovery and does not re-read it.

The next research question is what signals caused that boundary and whether a candidate policy can preserve the good SIMPLE cases while promoting disposable broad exploration more reliably.

## Cross-probe conclusion

Do **not** lower the SIMPLE threshold mechanically.

The current evidence supports three more specific experiments:

1. **Reclassification:** test whether Main should delay or explicitly revisit an early SIMPLE decision once inspection becomes repository-wide.
2. **Investigation vs assurance:** treat the need for isolated discovery and the need for a fresh final judgment as separate decisions. Probe 003 bought useful Architect evidence but still had no independent final review; that may be correct for a read-only audit, but the distinction becomes especially important after mutation.
3. **Tool ownership observability:** improve experiment analysis so Main/Council tool execution is attributable automatically rather than reconstructed manually from event parentage.

The target is not more subagent calls. The target is better placement of cheap independent inference passes.
